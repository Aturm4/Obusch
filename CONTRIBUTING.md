# Работа с репозиторием

## Изменения

1. Создайте ветку `feat/краткое-название`, `fix/краткое-название` или `chore/краткое-название` от актуальной `main`.
2. Свяжите изменение с Issue и укажите в Pull Request, что поменялось и как это проверено.
3. Дождитесь проверок `Secrets (Gitleaks)` и, если он есть в проекте, `Quality`.
4. Объедините Pull Request через squash merge. `main` должна оставаться пригодной к сборке.

Доступность обязательной защиты приватной ветки зависит от тарифа GitHub; сами CI-проверки работают независимо от наличия такой защиты.

## Проверка перед коммитом

Установите [pre-commit](https://pre-commit.com/#install), затем один раз в каждом локальном клоне выполните:

```bash
pre-commit install
pre-commit run --all-files
```

Конфигурация фиксирует версию Gitleaks и маскирует найденные значения. Установка hooks относится только к текущему клону; при новом клонировании её нужно повторить.

Для отдельного сканирования всей доступной истории используйте Gitleaks 8.30.1:

```bash
gitleaks git . --log-opts="--all --full-history -m" --config=.gitleaks.toml --ignore-gitleaks-allow --redact=100
```

## Секреты и данные

- Настоящие ключи, пароли, токены, приватные ключи и выгрузки пользовательских данных хранятся вне Git.
- `.env`, `.env.*`, `.dev.vars` и их локальные варианты игнорируются. В файлах `*.example` допустимы только пустые значения или явно вымышленные примеры.
- Настройки production задаются в secret-хранилище платформы деплоя. Тесты CI не должны требовать production-секретов.
- Перед публикацией скриншотов проверьте, что в них нет приватных данных и открытых панелей с ключами.
- При настоящей утечке сначала отзовите или замените ключ у провайдера. Затем удалите его из кода и согласуйте очистку истории; удаления последней версии файла недостаточно.
- Исключения сканера допустимы только для разобранных ложных срабатываний, с узким условием и объяснением. Не отключайте правило целиком ради одного совпадения.

GitHub Actions используют минимальные права, зафиксированные SHA сторонних actions и проверяемый checksum Gitleaks. Обновления зависимостей приходят отдельными Pull Request от Dependabot и проходят обычные проверки.
